# Retro: day-03 Prisma seed (2026-11-09)

The schema and `init` migration landed with `day-02` (ADR-009). This milestone adds the idempotent seed, verifies the migration on an empty database, and exposes Prisma Studio.

## Non-obvious constraints found during APPLY and VALIDATE

1. **Seed with `tsx`, not `ts-node`.** The handbook runs `ts-node prisma/seed.ts`, but `module: Node16` makes ts-node fail. tsx was already a dev dependency, so `"prisma": { "seed": "tsx prisma/seed.ts" }`.
2. **Board and Task have no natural unique key.** `upsert` needs a unique `where`, so the seed uses fixed v4 UUIDs. Every upsert uses `update: {}`, so a second run changes nothing, including the password hash.
3. **`prisma/seed.ts` sits outside `rootDir: src`.** This is the same trap as `tests/` (day-02 retro #3): `api/prisma/tsconfig.json` extends the root config with `rootDir: ".."`, and `npm run typecheck` runs it.
4. **A new native dependency needs `up --build -V`.** Without `-V`, the anonymous `/app/node_modules` volume keeps the old modules and `bcrypt` is missing. This applies to the dev and test stacks.
5. **Studio needs `--hostname 0.0.0.0` inside the container.** The host side is published as `127.0.0.1:5555:5555`, so it isn't exposed to the network (ADR-002 allows only this extra port).
6. **`migrate deploy` never seeds; `migrate dev`/`migrate reset` do.** The api start command and the test stack use `deploy`, so the test DB never receives seed rows.
7. **The seed password is read from env.** It comes from `SEED_USER_PASSWORD` through `env.ts` (Rule 5), not a constant. The seed exits with code 1 if it is unset or if `NODE_ENV=production`.
