## 1. Overview and scope

FlowBoard is a REST API for managing boards and tasks, similar to the backend of Trello or Jira. It is the capstone of the Node.js Engineering Program Part 2. A pass means the trainer can clone the repo, run `docker compose up`, run the test suite, and get correct answers to "why" questions at the Security Gate.

**In scope:** auth (JWT access and refresh tokens with rotation), boards CRUD, tasks CRUD, an audit log written asynchronously by a worker, Redis rate limiting and brute-force lockout, OWASP hardening, structured logging, health and readiness probes, and integration tests with at least 80% line and branch coverage.

**Out of scope:** any frontend or UI, real email, multi-user boards or sharing, roles and admins, pagination beyond `/audit-logs`, a production deployment target, Kubernetes, metrics and dashboards.

## 4. Data Model

## 4. Data model

This is the handbook schema with three deliberate additions, marked **(+)** and explained in [ADR-003](adr/ADR-003-ownership-via-board.md).

```prisma
generator client {
  provider = "prisma-client-js"
  binaryTargets = ["native", "debian-openssl-3.0.x"]   // (+) node:22-slim is Debian 12
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

model User {
  id        String     @id @default(uuid())
  email     String     @unique            // stored lower-cased
  password  String                        // bcrypt hash, never returned by the API
  createdAt DateTime   @default(now())
  boards    Board[]
  auditLogs AuditLog[]
}

model Board {
  id        String   @id @default(uuid())
  name      String
  ownerId   String
  owner     User     @relation(fields: [ownerId], references: [id])
  tasks     Task[]
  createdAt DateTime @default(now())

  @@index([ownerId])                                   // (+)
}

model Task {
  id          String     @id @default(uuid())
  title       String
  description String?
  status      TaskStatus @default(TODO)
  priority    Priority   @default(MEDIUM)
  boardId     String
  board       Board      @relation(fields: [boardId], references: [id], onDelete: Cascade)  // (+)
  createdAt   DateTime   @default(now())
  updatedAt   DateTime   @updatedAt

  @@index([boardId])                                   // (+)
}

model AuditLog {
  id        String   @id @default(uuid())
  userId    String
  user      User     @relation(fields: [userId], references: [id])
  action    String   // CREATED | UPDATED | DELETED
  entity    String   // "Task"
  entityId  String   // task id; no FK, so the row outlives a deleted task
  createdAt DateTime @default(now())

  @@index([userId, createdAt])                         // (+)
}

enum TaskStatus { TODO IN_PROGRESS REVIEW DONE }
enum Priority   { LOW MEDIUM HIGH }
```

- **There is no `Task.userId`.** Ownership is resolved as `task → board → ownerId`.
- **`AuditLog.entityId` has no foreign key on purpose.** A `DELETED` audit row must survive after its task is gone.

## 6. Request lifecycle — `PATCH /tasks/:id`

This is the walkthrough the Security Gate asks for:

1. The client sends `PATCH http://localhost/api/tasks/<id>` to Nginx on port 80.
2. Nginx matches `location /api/`, strips the prefix, and proxies to `http://api:3000/tasks/<id>`. It sets `X-Forwarded-For` and `X-Request-Id`.
3. The api middleware runs in this order: pino-http (gets a request ID and starts the timer) → helmet → cors → `express.json({ limit: '10kb' })` → router.
4. `authenticate` verifies the access JWT using only the signature and expiry, with no database or Redis call, and sets `req.user = { id }`. A missing or invalid token gives 401.
5. The handler parses `req.params` with `IdParamSchema` (UUID) and the body with `UpdateTaskSchema`, which strips unknown fields. A failure gives 422.
6. The handler loads the task with its board: a missing task gives 404, and `board.ownerId !== req.user.id` gives 403.
7. `prisma.task.update` sets only the fields Zod returned.
8. `publishTaskEvent` runs `XADD tasks:events * action UPDATED taskId … userId … payload … ts …`.
9. The api responds `200 { success: true, data: task }`, and pino-http logs the method, path, status and duration.
10. In parallel, the worker's `XREADGROUP GROUP audit-group worker-1 COUNT 10 BLOCK 5000 STREAMS tasks:events >` receives the message. The `taskUpdated` handler inserts an `AuditLog` row, then the worker runs `XACK`. If the handler fails, the message stays pending and is retried. On the 3rd failure the worker moves it to `tasks:events:dlq` ([ADR-006](adr/ADR-006-async-audit-worker.md)).

**About step 8:** if `XADD` fails, the task update has already committed. The api logs the error and still returns 200, so the user isn't blocked by audit infrastructure. That change will have no audit row. This trade-off is accepted and recorded in [ADR-006](adr/ADR-006-async-audit-worker.md).


## 7. Error Handling

## 7. Error handling

- **`AppError(message, statusCode, code)`** is defined in `src/errors/AppError.ts`, together with the `isAppError()` type guard and `globalErrorHandler`.
- **Async handlers** use `try/catch` and call `next(err)`. They never call `res.status().json()` inside a `catch`. This matters because Express 4 does not catch rejected promises.
- **Response shapes:**
  - Success: `{ success: true, data }`
  - Error: `{ success: false, message, code }`
  - Validation errors also include a `details` array ([ADR-007](adr/ADR-007-validation-contract.md)).
- **Mapping in `globalErrorHandler`**, checked in this order:

| Thrown | Status | `code` |
|---|---|---|
| `AppError` | its own | its own |
| `ZodError` | 422 | `VALIDATION_ERROR` (+ `details: [{ path, message }]`) |
| body-parser error with `type === 'entity.too.large'` | 413 | `PAYLOAD_TOO_LARGE` |
| body-parser error with `type === 'entity.parse.failed'` | 400 | `INVALID_JSON` |
| `Prisma…KnownRequestError` P2025 | 404 | `NOT_FOUND` |
| `Prisma…KnownRequestError` P2002 | 409 | `CONFLICT` |
| `jsonwebtoken` errors | 401 | `UNAUTHORIZED` |
| anything else | 500 | `INTERNAL_ERROR` |

- **Unknown routes:** a final `notFound` middleware turns any unmatched route into `404 ROUTE_NOT_FOUND`.
- **Production:** when `NODE_ENV=production`, responses never contain `stack` and 500 errors use the generic message "Internal server error". The full error, with its stack, is always logged server-side.


## 8. Authentication

## 8. Authentication

[ADR-004](adr/ADR-004-token-strategy.md) explains why the design is shaped this way.

- **Passwords** are hashed with bcrypt using `BCRYPT_COST`, default and minimum 12. Emails are lower-cased and trimmed before storage and lookup.
- **Access token:** `jwt.sign({ sub: userId }, JWT_ACCESS_SECRET, { expiresIn: '15m' })`.
- **Refresh token:** `jwt.sign({ sub: userId, jti: uuid }, JWT_REFRESH_SECRET, { expiresIn: '7d' })`. It is stored with `SET refresh:{userId}:{jti} 1 EX 604800`.
- **Separate secrets:** access and refresh tokens use different secrets, so a refresh token can never pass as an access token.
- **`authenticate`:** checks for `Authorization: Bearer <token>`, then runs `jwt.verify` with the access secret, then sets `req.user = { id: sub }`. It makes no database or Redis call.
- **Login:** a wrong email and a wrong password return the same `401 INVALID_CREDENTIALS`. When the email is unknown, the handler still runs `bcrypt.compare` against a dummy hash, so response timing doesn't reveal whether an account exists.

## 9. Redis

### 9.1 Client

`src/lib/redis.ts` is shared by the api and mirrored in the worker. The details are in [ADR-005](adr/ADR-005-redis-failure-policy.md).

```ts
new Redis({
  host: env.REDIS_HOST,
  port: env.REDIS_PORT,          // parsed by the env schema; never `Number(x) ?? 6379`
  enableOfflineQueue: false,     // fail fast when Redis is down, instead of queueing forever
  maxRetriesPerRequest: 1,
});
```

- The worker uses its **own connection** for the blocking `XREADGROUP` call. A blocked connection can't serve other commands.
- Errors are logged with the Pino logger, never with `console.error`.

### 9.2 Keyspace

| Key | Type | TTL | Written by | Purpose |
|---|---|---|---|---|
| `rate:auth:{ip}` | string (counter) | `RATE_LIMIT_WINDOW_SECONDS` (900) | api | Per-IP limit on login and register, shared bucket. Uses `MULTI INCR; EXPIRE NX`. |
| `login:fail:{email}` | string (counter) | `LOGIN_LOCKOUT_SECONDS` (900) | api | Failed logins per email. Deleted on a successful login. |
| `login:lock:{email}` | string | `LOGIN_LOCKOUT_SECONDS` (900) | api | Set when failures reach `LOGIN_MAX_FAILURES` (5). While it exists, login returns `429 ACCOUNT_LOCKED`. |
| `refresh:{userId}:{jti}` | string `"1"` | 604800 (7d) | api | Live refresh token. `DEL` on rotation and on logout. |
| `tasks:events` | stream | none | api `XADD` / worker `XREADGROUP` | Task events. Consumer group `audit-group`. |
| `tasks:events:dlq` | stream | none | worker | Dead-letter queue (§9.3). |

**Rate limiting is fail-open.** If any rate-limit or lockout command throws, the middleware logs at `warn` and calls `next()`. Only a 429 that the middleware decided itself is sent through `next(err)`.

### 9.3 Event and DLQ format

**Stream entry on `tasks:events`:**

| Field | Value |
|---|---|
| `action` | `CREATED` \| `UPDATED` \| `DELETED` |
| `taskId` | `<uuid>` |
| `userId` | `<uuid>` (the actor) |
| `payload` | `<JSON string>` (the task snapshot after the change; for `DELETED`, the snapshot before it) |
| `ts` | `<epoch ms>` |

**DLQ entry on `tasks:events:dlq`**, written with `XADD` by the worker after `WORKER_MAX_DELIVERIES` (3) failed deliveries:

| Field | Value |
|---|---|
| `originalId` | the stream ID in `tasks:events` |
| `action`, `taskId`, `userId`, `payload`, `ts` | copied unchanged |
| `error` | the last error message |
| `deliveries` | `3` |
| `failedAt` | `<ISO timestamp>` |

After the `XADD` to the DLQ, the worker runs `XACK tasks:events audit-group <originalId>`.

**Inspecting the DLQ:** `docker compose exec redis redis-cli XRANGE tasks:events:dlq - +`

The brief requires this format to also be copied into the AI context file (Day 14).

## 10. Observability

- **Logger:** `src/lib/logger.ts` uses level `LOG_LEVEL`, and pino-pretty only when `NODE_ENV=development`.
- **Redaction paths:**
  - `req.headers.authorization`
  - `req.headers.cookie`
  - `*.password`
  - `*.refreshToken`
  - `*.accessToken`
  - `body.password`
  - `body.refreshToken`
- **pino-http** is the first middleware.
  - **Request ID:** it uses `genReqId` to take Nginx's `X-Request-Id` when present, otherwise `randomUUID()`, and echoes the ID back in the `X-Request-Id` response header.
  - **Log line:** it logs the method, URL, status code and `responseTime`.
  - **Bodies:** request bodies are not logged by default. Any body logged explicitly passes through redaction.
- **`GET /health`:** returns `200 { success: true, data: { status: 'ok', uptime } }`, with no dependency checks.
- **`GET /ready`:** runs `SELECT 1` through Prisma and `PING` on Redis in parallel, each with a 2s timeout. It returns `200 { success: true, data: { status: 'ready', db: 'ok', redis: 'ok' } }` when both pass, or `503 NOT_READY` through `AppError` if either fails.
- **Worker logging:** the worker uses the same Pino logger configuration. It logs at `info` for each processed event, at `warn` for each retry, and at `error` for each DLQ move.

## 12. Security Rules

## 12. Security rules

These rules are non-negotiable and become AI context file rules:

1. **Bearer auth** on every board, task and audit route. Only `/auth/*`, `/health` and `/ready` are public.
2. **Ownership** is checked in every handler that loads a board or task by id ([ADR-003](adr/ADR-003-ownership-via-board.md)). List routes filter by `ownerId`.
3. **Zod on all input:** every body, param and query string is parsed with Zod. Never spread `req.body` into Prisma. Use plain `z.object()`, with no `.passthrough()` and no `.strict()` ([ADR-007](adr/ADR-007-validation-contract.md)).
4. **No raw SQL**, except the literal `SELECT 1` in `/ready`.
5. **No secrets in code.** Every secret comes from env. `.env` is git-ignored.
6. **No sensitive data in output:** no password or hash in any response or log, and no stack trace in production responses.
7. **Middleware:** helmet with defaults, CORS restricted to `ALLOWED_ORIGINS`, `express.json({ limit: '10kb' })`, and `app.set('trust proxy', 1)`.
8. **Async middleware** wraps its body in `try/catch` and calls `next(err)`, because Express 4 does not catch async throws.

## Adr-001: Container Runtime, Images And Startup

# ADR-001: Container runtime, images and startup

- **Status:** Accepted
- **Date:** 2026-11-09
- **Epic:** EPIC-FOUNDATION

## Context

Every service must start with a plain `docker compose up` on a fresh clone. Two dependencies make the image choice matter:

- **Prisma** ships a native query engine that depends on OpenSSL.
- **bcrypt** builds native code with node-gyp.

## Decision

1. **Base image:** both `api` and `worker` use `node:22-slim` (Debian 12), not Alpine.
   - Alpine uses musl. Prisma then needs a separate engine target, and bcrypt often falls back to a source build that needs python, make and g++.
   - `slim` images don't include OpenSSL, so each Dockerfile runs `apt-get install -y --no-install-recommends openssl ca-certificates`.
   - The Prisma generator lists `binaryTargets = ["native", "debian-openssl-3.0.x"]`.
2. **Node 22 LTS**, which the brief allows ("22 or 24"). Node 22 has the widest compatibility with Prisma 5 and Jest 29.
3. **Dev target:** the Compose stack uses a `dev` build stage. The source is bind-mounted, `node_modules` sits in an anonymous volume so the mount doesn't hide it, and `tsx watch` gives hot reload. A `prod` stage (`tsc`, then `node dist/server.js`) is backlog.
4. **Migrations on start:** the api command is `npx prisma migrate deploy && npx tsx watch src/server.ts`. A fresh clone gets its tables with no manual step, which the brief §5.1 requires ("without manual intervention"). During development, `prisma migrate dev` is still run by hand to create new migrations.
5. **Worker Prisma client:** the worker's build context is the repo root. Its Dockerfile copies `api/prisma/schema.prisma` and runs `prisma generate --schema`. The api owns the schema and the migrations; the worker only generates a client. Both pin the same Prisma version.
6. **Startup order:** `db` and `redis` have healthchecks, and `api` and `worker` use `depends_on: condition: service_healthy`.

## Consequences

- **Larger images:** the api image is about 200 MB larger than an Alpine image. That is acceptable for a training project.
- **Version drift:** the schema has one source, but the worker's `@prisma/client` version must be bumped together with the api's.
- **Bad migrations block startup:** a failed migration stops the api from starting, which is what we want.

## Alternatives considered

- **Alpine with `openssl` and build tools:** works, but brings more surprises and slower builds.
- **Copying the schema into the worker:** two schemas would drift apart.
- **A shared `packages/db` workspace:** cleaner, but it adds monorepo tooling the brief doesn't ask for.


## Security Gate One-Liner

## Security Gate one-liner

> "Tests hit a real Postgres and Redis in a separate Compose project, so they can't touch dev data. Jest runs serially with a truncate before each test, and the coverage threshold is enforced in config, so a drop fails the build."


## Adr-002: Nginx Strips `/Api`; The Api Is Reachable Only Through Nginx

# ADR-002: Nginx strips `/api`; the API is reachable only through Nginx

- **Status:** Accepted
- **Date:** 2026-11-09
- **Epic:** EPIC-FOUNDATION, EPIC-SECURITY

## Context

The brief says Nginx "forwards /api/\* traffic to the api service". The handbook and its tests call routes without a prefix, as in `request(app).post('/auth/register')`.

The rate limiter keys on `req.ip`. Behind a proxy, `req.ip` is only correct when `trust proxy` is set. If the api were also reachable directly, a client could forge `X-Forwarded-For` and get a fresh rate-limit bucket on every request.

## Decision

1. **Nginx strips the prefix:**
   ```nginx
   location /api/ {
     proxy_pass http://api:3000/;          # trailing slash strips /api
     proxy_set_header Host $host;
     proxy_set_header X-Real-IP $remote_addr;
     proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
     proxy_set_header X-Forwarded-Proto $scheme;
     proxy_set_header X-Request-Id $request_id;
   }
   ```
   - Express mounts its routes at the root: `/auth`, `/boards`, `/tasks`, `/audit-logs`, `/health` and `/ready`.
   - Clients call `http://localhost/api/tasks`.
   - Supertest calls `/tasks`.
2. **`app.set('trust proxy', 1)`:** Express trusts exactly one hop, Nginx. `req.ip` becomes the address Nginx saw, and any client-supplied entries further left in `X-Forwarded-For` are ignored.
3. **The `api` port is not published to the host.** Compose uses no `ports: 3000:3000`, so all traffic goes through Nginx. `db` and `redis` aren't published either; use `docker compose exec` to reach them. The only extra port is 5555 on the api, for Prisma Studio.
4. **`client_max_body_size 16k`** in Nginx sits above the api's 10kb limit. Express then returns the JSON 413 itself, rather than Nginx returning an HTML 413.

## Consequences

- **Postman setup:** the Postman or Bruno base URL is `http://localhost/api`.
- **Tests skip Nginx:** Supertest bypasses Nginx, so tests run without `X-Forwarded-For` and `req.ip` is the loopback address. Each test file resets Redis, so they don't share a rate-limit bucket.
- **Spoofing defence:** rate-limit keys can't be spoofed, because the only path to the api runs through the one trusted hop.


## Adr-003: Ownership Is Resolved Through `Board.Ownerid`

# ADR-003: Ownership is resolved through `Board.ownerId`

- **Status:** Accepted
- **Date:** 2026-11-09
- **Epic:** EPIC-API, EPIC-DATA

## Context

- **No owner field on tasks:** the handbook's OWASP table says to check `task.userId === req.user.id`, but the schema's `Task` model has no `userId` column.
- **Board deletes fail as written:** the handbook schema has no `onDelete` on `Task.board`. Deleting a board that has tasks would hit a foreign key violation (P2003) and return a 500.
- **403, not 404:** the brief requires a 403 when a user touches another user's resource.

## Decision

1. **A task belongs to the owner of its board.** No `userId` is added to `Task`, so there is no second ownership field that could fall out of sync.
2. **Check order:** load the resource first, then check ownership.
   - **Single board:** `findUnique`; 404 `BOARD_NOT_FOUND` if missing; 403 `FORBIDDEN` if `ownerId !== req.user.id`.
   - **Single task:** `findUnique({ include: { board: { select: { ownerId: true } } } })`; 404 `TASK_NOT_FOUND`, otherwise 403 as above.
   - **`POST /tasks`:** checks the `boardId` in the body the same way. 404 if the board doesn't exist, 403 if it belongs to someone else.
   - **List routes** filter in the query (`where: { ownerId }` or `where: { board: { ownerId } }`), so they never return other users' rows and never need a 403.
3. **One shared helper:** a small set of functions (`getOwnedBoard(id, userId)` and `getOwnedTask(id, userId)`) holds the check, so every route behaves the same way.
4. **Schema additions (deviations from the handbook):**
   - `Task.board` gets `onDelete: Cascade`, so deleting a board removes its tasks.
   - Indexes go on `Board.ownerId`, `Task.boardId` and `AuditLog(userId, createdAt)`.

## Consequences

- **IDs can be probed:** a 403 tells the caller that the ID exists. Returning 404 for "not yours" would hide that, but the brief explicitly requires 403. UUIDs make guessing IDs impractical, so this leak is accepted.
- **Board delete has no per-task audit:** cascaded task deletes don't publish `TASK_DELETED` events, so they get no audit rows. This is tracked as OQ-7.


## Adr-004: Access And Refresh Tokens, With Refresh Rotation In Redis

# ADR-004: Access and refresh tokens, with refresh rotation in Redis

- **Status:** Accepted
- **Date:** 2026-11-09
- **Epic:** EPIC-AUTH

## Context

The brief requires:

- a 15-minute access token and a 7-day refresh token;
- refresh tokens rotated on each use;
- a replayed refresh token rejected with 401;
- logout that revokes the refresh token.

Checking an access token must not need a database or Redis call (brief §2.2, step 3).

## Decision

1. **Access token:** a JWT `{ sub }` signed with `JWT_ACCESS_SECRET`, valid for 15 minutes. It is stateless and can't be revoked before it expires.
2. **Refresh token:** a JWT `{ sub, jti }` signed with a **different** secret, `JWT_REFRESH_SECRET`, valid for 7 days. The server stores it as `SET refresh:{sub}:{jti} 1 EX 604800`.
3. **`POST /auth/refresh`**, with `{ refreshToken }` in the body:
   1. `jwt.verify` with the refresh secret. A bad signature or an expired token returns 401.
   2. `DEL refresh:{sub}:{jti}`. If the result is `0`, the token was already used or revoked, so return 401 `INVALID_REFRESH_TOKEN`.
   3. Issue a new pair with a new `jti`, `SET` it with the TTL, and return `{ accessToken, refreshToken }`.

   Step 2 uses the return value of `DEL` rather than a separate `EXISTS` then `DEL`. That makes the check-and-consume atomic, so two concurrent refreshes with the same token can't both succeed.
4. **`POST /auth/logout`**, with `{ refreshToken }` in the body:
   - verify the token (401 if it's invalid);
   - `DEL` its key;
   - return 204, even if the key was already gone, so logout can safely be called twice.
5. **Redis fails closed for refresh:** if Redis is down, refresh returns 503. A refresh must never succeed without the revocation check. Rate limiting fails open instead ([ADR-005](ADR-005-redis-failure-policy.md)).
6. **Token issuing:** `src/lib/tokens.ts` holds `issueTokenPair`, `verifyAccess` and `verifyRefresh`, so the sign and verify options live in one place.

## Consequences

- **Short window after logout:** an access token that was already issued stays valid for up to 15 minutes after logout. That is the standard trade-off for stateless access tokens, and the brief accepts it.
- **Separate secrets:** a refresh token presented as a Bearer token fails verification.
- **Out of scope:** reuse detection, meaning "a replayed token revokes the whole token family", is a real-world improvement that the brief doesn't require.


## Adr-005: Redis Client Settings And Failure Policy

# ADR-005: Redis client settings and failure policy

- **Status:** Accepted
- **Date:** 2026-11-09
- **Epic:** EPIC-REDIS, EPIC-OBSERVABILITY

## Context

The brief says a Redis failure in the rate limiter must be "handled gracefully". The API must not crash or block all traffic. It also requires `/ready` to return 503 when Redis is down. The handbook's example code breaks both requirements:

1. **Port fallback never applies:** `Number(process.env.REDIS_PORT) ?? 6379` never falls back, because `Number(undefined)` is `NaN`, and `??` only replaces `null` or `undefined`.
2. **Commands hang while Redis is down:** by default ioredis queues commands while disconnected. The rate limiter and `/ready` then hang instead of failing.
3. **Async throws are lost:** the rate limiter throws inside an `async` middleware, and Express 4 doesn't catch that. The result is an unhandled rejection and a request that never gets a response.
4. **A counter can lose its expiry:** a separate `INCR` followed by `EXPIRE` can leave a key with no TTL if the process dies in between.

## Decision

1. **Typed env values:** env values are parsed with `z.coerce.number().default(6379)` in `config/env.ts`. Nothing else reads `process.env`.
2. **Client options:** `enableOfflineQueue: false, maxRetriesPerRequest: 1`. Commands reject quickly while Redis is down, and ioredis keeps reconnecting in the background.
3. **Rate limiter:**
   ```ts
   try {
     const [[, count]] = await redis.multi().incr(key).expire(key, WINDOW, 'NX').exec();
     if (count > MAX) return next(new AppError('Too many requests', 429, 'RATE_LIMIT_EXCEEDED'));
     return next();
   } catch (err) {
     logger.warn({ err }, 'rate limiter unavailable — failing open');
     return next();
   }
   ```
   - **Atomic:** `MULTI` sends both commands as one unit, and `EXPIRE … NX` only sets the TTL on the first hit.
   - **Response headers:** the limiter sets `RateLimit-Limit`, `RateLimit-Remaining` and `Retry-After` (on 429).
4. **Failure policy for each Redis use:**

   | Use | Policy | Reason |
   |---|---|---|
   | Rate limiter | Fail **open** (log `warn`, continue) | A cache outage must not lock every user out. Bcrypt cost 12 still slows brute force. |
   | Login lockout | Fail **open** | Same reason. |
   | Refresh / logout | Fail **closed** (503) | Skipping the revocation check would let a revoked token through. |
   | `publishTaskEvent` | Log `error`, still return 2xx | The task change is already committed ([ADR-006](ADR-006-async-audit-worker.md)). |
   | `/ready` | 503 `NOT_READY` | That is its purpose. |

5. **Readiness timeouts:** `/ready` wraps each check in a 2s timeout (`Promise.race`), so a dependency that hangs can't hang the probe.

## Consequences

- **Rate limits lapse during an outage:** while Redis is down, rate limiting is effectively off. The `warn` logs make this visible.
- **Test needed:** the brief requires a test for the fail-open path. Mock `redis.multi` to throw, then expect the request to go through.


## Adr-006: Audit Log Written Asynchronously, Through A Redis Streams Consumer Group

# ADR-006: Audit log written asynchronously, through a Redis Streams consumer group

- **Status:** Accepted
- **Date:** 2026-11-09
- **Epic:** EPIC-EVENTS

## Context

Every task create, update and delete must produce an `AuditLog` row, and the user must not wait for that write. The brief requires:

- a Redis Stream named `tasks:events`;
- a consumer group named `audit-group`;
- `XACK` after each event is processed;
- failed messages moved to a dead-letter queue after 3 retries;
- the DLQ format documented.

## Decision

1. **The API publishes** with `publishTaskEvent({ action, taskId, userId, payload })`, which runs `XADD tasks:events * …`. It is called after the Prisma write succeeds. If the `XADD` fails, the error is logged and the API response is unaffected.
2. **The worker starts up** like this:
   - It runs `XGROUP CREATE tasks:events audit-group $ MKSTREAM` and ignores a `BUSYGROUP` error.
   - It uses `$`, so a new group starts at new messages only, which avoids replaying old history after a reset.
3. **The main loop** runs `XREADGROUP GROUP audit-group ${WORKER_CONSUMER_NAME} COUNT 10 BLOCK 5000 STREAMS tasks:events >` on a dedicated Redis connection.
   - **Dispatch:** each message goes to `handlers/task{Created|Updated|Deleted}.ts` according to its `action`.
   - **Success:** the handler inserts the `AuditLog` row, then the worker runs `XACK`.
   - **Failure:** the worker doesn't `XACK` the message, so it stays in the pending entries list.
4. **Retries:** on each loop pass, the worker first runs `XAUTOCLAIM tasks:events audit-group <consumer> ${WORKER_CLAIM_IDLE_MS} 0-0 COUNT 10`. This picks up messages that have been pending too long.
   - **Delivery count:** `XPENDING tasks:events audit-group - + 10` (the extended form) returns each message's delivery count.
   - **Count below `WORKER_MAX_DELIVERIES` (3):** process the message again.
   - **Count at 3:** if processing still fails, run `XADD tasks:events:dlq * originalId … error … deliveries … failedAt …` plus the original fields, then `XACK` the original. The full format is in ARCH §9.3.
5. **Idempotent handlers:** delivery is at-least-once, so the `AuditLog` insert can't use a natural key. For now, a duplicate row after a crash between the insert and `XACK` is accepted (see Consequences).
6. **Shutdown:** SIGTERM or SIGINT sets `stopping = true`. The worker finishes the current batch, then runs `prisma.$disconnect()` and `redis.quit()` on both connections, then exits 0. Compose's 10s stop grace covers the 5s `BLOCK`.

## Consequences

- **Gap if `XADD` fails:** a task change can exist without an audit row. The API logs the missed event at `error`, so the gap is visible. A transactional outbox would close it, but that is outside the brief.
- **Possible duplicates:** a crash between the `AuditLog` insert and `XACK` can produce a duplicate audit row. The fix, a unique stream-ID column on `AuditLog`, is backlog.
- **One consumer is enough:** a single consumer (`worker-1`) meets the brief. Consumer groups would allow scaling to more workers without code changes.


## Adr-007: Zod Validation Contract

# ADR-007: Zod validation contract

- **Status:** Accepted
- **Date:** 2026-11-09
- **Epic:** EPIC-API, EPIC-SECURITY

## Context

The brief requires:

- every body to have a Zod schema;
- ID path params to be validated as UUIDs;
- invalid input to return 422 with a descriptive message;
- unknown fields to be **stripped**, not passed through or rejected;
- no mass assignment.

## Decision

1. **Plain `z.object()`:** Zod strips unknown keys by default.
   - Never `.passthrough()`, which lets fields like `isAdmin` through.
   - Never `.strict()`, which would turn an extra field into a 422 instead of stripping it.
2. **Parse everything:** handlers parse `req.params`, `req.query` and `req.body`, then use **only** the parsed result. Prisma `data` is built from that parsed object, and `req.body` is never spread into it.
3. **Schemas:**
   - **`IdParamSchema`:** `{ id: z.string().uuid() }`.
   - **`CreateTaskSchema`:**
     - `title`: string, 1–255 characters, trimmed;
     - `description`: string, at most 5000 characters, optional;
     - `priority`: `LOW` | `MEDIUM` | `HIGH`, default `MEDIUM`;
     - `status`: `TaskStatus`, optional;
     - `boardId`: UUID.
   - **`UpdateTaskSchema`:**
     - `title`, `description` (nullable), `priority` and `status` are all optional;
     - a refinement requires at least one field;
     - `boardId` can't be changed;
     - allowing `status` is an assumption tracked as OQ-1.
   - **`CreateBoardSchema`:** `name`, string, 1–100 characters, trimmed.
   - **`RegisterSchema` / `LoginSchema`:**
     - `email`: email address, lower-cased;
     - `password`: 8–72 characters (bcrypt ignores bytes after the 72nd).
   - **`RefreshSchema` / `LogoutSchema`:** `refreshToken`, a non-empty string.
   - **`TaskListQuery`:** `boardId`, UUID, optional.
   - **`AuditLogQuery`:** `limit`, coerced integer, 1–100, default 50.
4. **Error body:** a `ZodError` becomes a 422 response:
   ```json
   { "success": false, "message": "Validation failed: title is required", "code": "VALIDATION_ERROR",
     "details": [{ "path": "title", "message": "Required" }] }
   ```
   - **`message`** names the first issue, which keeps it descriptive.
   - **`details`** is an addition to the handbook's error shape, and it appears only on 422 responses.
5. **Schema location:** schemas live in `src/schemas/`, and handlers type their input with `z.infer`, so there are no duplicate interfaces.

## Consequences

- **Silent stripping:** clients get no error for a misspelled optional field, because it is simply ignored. This is exactly what the brief asks for.
- **Mass assignment test:** `POST /tasks` with `{ …, isAdmin: true, id: "x" }` returns 201, and the stored task has neither field.


## Adr-008: Integration Tests Against Real Postgres And Redis In An Isolated Compose Project

# ADR-008: Integration tests against real Postgres and Redis in an isolated Compose project

- **Status:** Accepted
- **Date:** 2026-11-09
- **Epic:** EPIC-TESTING

## Context

The trainer runs `docker compose -f docker-compose.test.yml exec api npx jest` exactly as written. The brief requires a separate test database, at least 80% line and branch coverage, and a happy-path test plus an error-path test for every endpoint. Two things about that command matter:

- **Same project name:** with no `name:` in the file, Compose would use the directory name as the project name, the same as the dev stack. Services with the same names would then replace the dev containers.
- **Parallel workers:** `npx jest` with no flags runs test files in parallel workers, and those would race on one database.

## Decision

1. **Standalone test stack:** `docker-compose.test.yml` is a complete file, not an override, and its first line is `name: flowboard-test`.
   - **`api`:** built from the same Dockerfile, with `NODE_ENV=test` and the test `DATABASE_URL`. Its command runs `prisma migrate deploy`, then keeps the container alive for `exec`.
   - **`db`:** `postgres:16` with storage in `tmpfs`, so it is fast and disposable.
   - **`redis`:** `redis:7`.
   - **Not included:** there is no worker and no Nginx.
2. **Workflow:** `docker compose -f docker-compose.test.yml up -d --build`, then the brief's command, unchanged. The README documents both lines.
3. **Jest configuration** (`api/jest.config.ts`), so the bare `npx jest` behaves correctly:
   - **`maxWorkers: 1`:** test files run one at a time.
   - **`globalSetup`:** checks that `NODE_ENV === 'test'` and that the database name ends in `_test`, and refuses to run otherwise.
   - **`setupFilesAfterEnv`:** runs `TRUNCATE "AuditLog","Task","Board","User" CASCADE` and `redis.flushdb()` in `beforeEach`.
   - **Coverage:** `collectCoverage: true`, with `collectCoverageFrom: ['src/**/*.ts', '!src/server.ts', '!src/types/**']`.
   - **Threshold:** `coverageThreshold: { global: { lines: 80, branches: 80 } }`, so a coverage drop fails the run.
4. **Supertest** imports `app` from `src/app.ts` and never starts a server. Routes have no prefix (ADR-002).
5. **Test helpers** live in `tests/helpers/`:
   - `registerAndLogin()` returns `{ user, accessToken, refreshToken }`.
   - `createBoard(token)` creates a real board. The handbook's `boardId: 'some-uuid'` example fails UUID validation, so tests need a real board.
6. **Required test cases** are listed in the requirements doc, §4. They include register (success and duplicate email), login (success and wrong password), refresh, replay, logout, 403 for another user's task, 413 above 10kb, Helmet headers, mass-assignment stripping, no stack trace in production (`NODE_ENV` stubbed within the test), the rate limiter returning 429, the rate limiter failing open (Redis mocked to throw), lockout, and `/ready` returning 503 (Prisma or Redis mocked to reject).
7. **Worker tests:** the event-publishing tests assert `XLEN tasks:events` and the fields of the last entry. They don't test the worker. Worker handlers get separate unit tests in `worker/`, with no coverage threshold (OQ-6).
8. **Tests ship with features:** each feature commit includes its tests. Day 6 of the 7-day plan only closes coverage gaps.

## Consequences

- **Serial runs are slower**, but deterministic.
- **Stack must be up:** the trainer has to run `up -d` before the `exec` command. The README states this, and so does the test command's preamble.


## Adr-009: Commit Message Convention

# ADR-009: Commit message convention

- **Status:** Accepted
- **Date:** 2026-11-09
- **Epic:** EPIC-FOUNDATION

## Context

The brief requires 15 milestone commits whose messages start with an exact tag, for example `day-01: environment setup, AppError, global error handler`. The trainer checks the git history against that list.

This repo's tooling expects Conventional Commits:

- the `/commit` command writes `feat(scope): …`;
- `/scaffold` installs commitlint with `@commitlint/config-conventional`.

With that commitlint config, a `day-01: …` message is **rejected**, because `day-01` isn't a valid type.

## Decision

1. **Milestone commits** use the brief's tag and text **exactly**, in the brief's order, with one commit per tag.
2. **Every other commit** (work in progress, fixes, docs) uses Conventional Commits. Extra commits between milestones are allowed.
3. **commitlint** may be installed, but its config must accept the milestone pattern. One way is to extend `config-conventional` and add an `ignores` rule:
   ```js
   ignores: [(msg) => /^(day-\d{2}|week-0[1-3] complete):/.test(msg)]
   ```
   The simpler option is to leave commitlint out entirely (see the scaffold notes). Husky with lint-staged, which runs lint and format checks before each commit, is fine either way.
4. **No backdating.** The compressed schedule puts about 2 milestone commits on each day (OQ-3).

## Consequences

- **`/commit` needs guidance:** the `/commit` command has to be told when a commit is a milestone. The AI context file lists the 15 tags.

## Milestone tags (from brief §4)

| # | Tag | 7-day plan day |
|---|---|---|
| 1 | `day-01: environment setup, AppError, global error handler` | 1 |
| 2 | `day-02: typed task routes with Zod validation` | 2 |
| 3 | `day-03: prisma schema, migration, seed data` | 2 |
| 4 | `day-04: boards CRUD, full route layer` | 3 |
| 5 | `week-01 complete: API, auth foundation, Prisma schema` | 3 |
| 6 | `day-06: Redis client, rate limiter middleware` | 4 |
| 7 | `day-07: refresh token rotation, logout endpoint` | 4 |
| 8 | `day-08: Redis Stream events, worker consumer, AuditLog integration` | 5 |
| 9 | `day-09: integration test suite` | 6 |
| 10 | `week-02 complete: Redis, worker, auth hardening, test suite` | 6 |
| 11 | `day-11: Helmet, CORS, ownership checks` | 6 |
| 12 | `day-12: brute-force protection, mass assignment prevention` | 6 |
| 13 | `day-13: Pino structured logging` | 7 |
| 14 | `day-14: health checks, DLQ documentation` | 7 |
